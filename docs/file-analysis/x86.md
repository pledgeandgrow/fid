# x86.fd

- **Path:** `compiler/x86.fd`
- **LOC:** 1,779 (Rust `src/x86.rs`: 1,420)
- **Role:** The *alternate* x86-64 backend — a **stack machine** (every SSA value lives at a fixed `%rbp` offset, `RAX`/`RCX` as working registers), emitting AT&T-syntax GAS assembly text for `elf64`'s assembler. The Rust reference calls it `build_x86_linux` — the no-PIR, no-regalloc path.

## Where called

**WIRED since 2026-10-23** — exactly via the suggested re-entry point.

- `compiler/compiler.fd:55` — `use compiler::x86`; `build_x86_linux` at `:1912`
  (IrModule → `X86CodeGen` asm text → elf64 assemble → link), exported.
- `compiler/main.fd` — `build-x86` command → `cmd_build_x86` → `build_x86_linux`
  (`fidesc build-x86 <file> -o out`, ELF only, x86-64). Also `use compiler::x86` at :30.
- The `codegen` command was also restored (see main.md) — this backend is now
  reachable two ways. Previously it was the fourteenth dead module: the PIR-L3
  path (`codegen_x64` + `regalloc` + `elf64`) is still the default `x86-64` route.

## Findings

### INFO — now wired; the port fidelity below matters again

No defects found that matter (nothing can reach it), but the port itself is solid — verified:

- **Inst coverage 43/43** — identical arm set to Rust's `gen_inst` (no missing/extra instructions).
- **`gen_int_binop` correct**: `cqto` + `idivq` for `Div`/`Mod` (remainder via `movq %rdx,%rax` — correct RDX:RAX semantics), shifts via `%cl`, comparisons via `cmp`+`set*`.
- **Stack discipline**: frame alloc (`subq $size, %rsp`), call-site `subq $8` 16-byte alignment before `call` (:673/:723), arg regs RDI/RSI/RDX/RCX/R8/R9 + stack-args spill — SysV-correct.
- **`gen_runtime_stubs`**: `p_print_int` (digit-extract loop w/ `divisor=10`, `movb $10` newline) etc. — the same hand-GAS runtime the module claims.
- **`escape_string` 1:1**: same escape set (`"` `\` `\n` `\r` `\t` `\0`), ASCII-printable passthrough, `\xNN` hex fallback for the rest.
- **`mangle_name`**: `main`/`_start`/`__pledge*`/`p_*` kept verbatim — same exemptions as Rust.
- **`wln` emit density**: 678 vs 673 emission sites — near-identical codegen volume.

### Inherited shape (would matter if wired)

- Stack-machine codegen is *correct but slow* — every value round-trips memory; that's the design (Rust comments call it "a starting point"), not a bug.
- Now wired, it produces AT&T text that `elf64.fd`'s assembler consumes — **caution:** elf64's assembler has documented gaps (off-by-one mem-operand decode, no `movapd`, no `jo` — see elf64.md). The stack-machine backend emits a simpler mnemonic set, but float/`jo` code will still hit those gaps.
