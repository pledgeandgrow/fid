# x86.fd — x86-64 stack-machine backend (`fid build-x86`)

Re-audited 2026-11-09 (previous audit 2026-10-22/23).

- **Path:** `compiler/x86.fd`
- **LOC:** 1,779 (Rust `src/x86.rs`: 1,420)
- **Role:** the simplest native backend: IR → AT&T x86-64 text, every
  SSA value in an `%rbp` slot, rax/rcx as working registers, its own
  `_start` and runtime stubs in asm. Assembled by `elf64.fd`, linked by
  `linker.fd` with an empty runtime.

## Where it is called

| Caller | What |
|--------|------|
| `compiler.fd` `build_x86_linux` (`use compiler::x86`) | `generate_asm_x86(ir_mod)` |
| `main.fd` `cmd_build_x86` | `fid build-x86 <file> [-o out]` |

Only command: `fid build-x86`. (The old doc said the `codegen` command
also reaches it: it does not, `codegen` uses codegen_x64.)

## Findings

### Verified live (2026-11-09, `s18.exe`)

1. **HIGH — `fid build-x86` produces a binary that crashes.** For
   `fn main() -> i64 { print("hi\n"); return 3; }` it printed "Built
   native executable" and wrote 120 bytes: ELF header and one program
   header, no code. Run in WSL: segmentation fault. Cause is downstream:
   elf64's 56-byte section headers (elf64.md 1) make the linker see no
   `.text` (linker.md 1). Nothing in this file was found to cause it.

### Code inspection

2. **INFO — port fidelity** (43/43 IR instruction arms, SysV argument
   registers, `cqto`/`idivq`, 16-byte call alignment, escape and mangle
   helpers) — from the 2026-10-22 audit, not re-checked.
3. **INFO — semantics lag the current IR.** The asm runtime stubs predate
   proposal 0004 (counted strings, 40-byte Vec header) and the shared
   core `Vec_*`; output that links would still need a check against
   `fid run`. Not re-checked in detail.

## Fix order

1. Fix elf64's section headers, then run `build-x86` on a few tests in WSL.
2. Decide whether to keep this backend: `fid emit --target x86_64-linux`
   (nat_ir) covers the same target with the stdlib.
