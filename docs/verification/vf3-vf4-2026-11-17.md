# VF3 and VF4: the long runs, Nov 17

Roadmap: [competitive-roadmap.md § Track VF](../roadmap/competitive-roadmap.md#track-vf--verification-in-place-of-years),
VF3 (coverage-guided fuzzing: no input may crash the compiler) and VF4
(every optimizer pass on and off over the whole suite: no output may
change). Tools: [README.md](README.md).

This batch could not build a compiler (the tree is built once, at the end
of the run, by its validation phase). So it did three things: it made the
long runs possible and cheap enough to finish (below, "Tools"), it ran what
the compiler it had (the stage 0 of Nov 16, `fid` at -O2) can run, and it
wrote the commands that the validation phase runs with the new compiler.
**The coverage-guided run and the whole-suite toggle runs have not been
run yet**; their results go in the last section when they are.

## Runs with the stage 0 of Nov 16 (no coverage)

Windows, `FID_HOME` the repository, tests of Nov 17 as the corpus (1,580
files under 20 KB of `tests/bootstrap`).

| Run | Inputs | Time | Findings |
|-----|--------|------|----------|
| `fuzz_frontend.py -n 1500 --seed 1117` (check) | 1,500 | 12.6 min | 1: F1 (input 218, 5000 nested brackets: `Panic: Stack overflow` in `Parser_parse_comparison` ...) |
| `--mode emit --target nat -n 120 --seed 2117` | 120 | 6.0 min | 1: F1 again (input 29, `Parser_parse_primary`) |
| `--mode emit --target x86_64-linux -n 80 --seed 3117` | 80 | 3.5 min | 1: F1 again (input 20, `Parser_parse_primary`) |

No input crashed the IR optimizer or the machine layer, and none hung; no
finding failed to reproduce. These are short (1,700 inputs in all) and
without coverage: they are a check of the tools on today's corpus, not the
long run.

F1 is the only crash: the parser recurses once per nesting level. Measured
on this compiler: 1,500 nested parentheses check, 2,000 overflow the
stack. The fix is the parser's (compiler/parser.fd, not this batch's
files): a limit of 256 levels counted where every level passes
(`parse_unary` for brackets and prefix operators, `parse_block` for
blocks), then one error, "nested too deeply", with the place; the parse
stops there (no cascade). The tests:
`tests/bootstrap/test_verify_parser_nesting_ok.fd` (200 levels of
parentheses, `-`, `!`, `-(` and blocks: prints 42, 7, true, -5, 200; passes
today on `run` and `emit`), `tests/bootstrap/test_verify_parser_nesting_limit_fail.fd` (300
parentheses must be rejected with "nested too deeply"; today it compiles,
so it fails until the fix is in), and `tests/verify/bugs/f1_parser_deep_nesting.fd`
(3000 levels: now expects the error instead of output).

VF4 smoke run of the new runner (stage 0, `emit`, `-j 1`): iropt-gvn, dse,
ssa over the 12 `test_opt_*` tests, hello and
`test_verify_opt_dse_sccp_iv`: no output changed; gvn changed 9 binaries
of 12, dse 12, ssa 0 (the stage 0 predates `ssa` being on by default).
Pruning skipped one build (hello, gvn): `dse`, `promote`, `fold` and
`sccp` change functions of core in every program, so the counters prune
little; the passes without a counter cannot be pruned at all. A second
start with `--resume` took 0.9 s (36 results reused).

  units), then 1,209 base and 5 x 1,209 variant emits: ~7,300 emits, about
  1.5 h at `J=8`.

  inputs and 1,000 per emit mode, each run twice (plain and instrumented).
