# VF15: the parser fuzzer's run of Nov 18, 2026

`scripts/fuzz/fuzz_parsers.py` (driver `tests/fuzz/parsers.fd`): each input
is a mutant of a seed of its format, written to a file, and the driver
built through C runs that format's parser on it. A finding is a panic, a
crash or a hang (20 s) that happens again on a second run.

**Compiler**: the stage 0 of Nov 16 (it does not hold the work of Nov 17-18),
Windows x64, `CC="zig cc"`, the driver built with `ccompile` from the
repository root, so with the **working tree's** stdlib (today's core.fd,
xml.fd, regex.fd, url.fd, tls_record.fd; checked: the generated C has core's
region functions). The machine ran other sessions' fid builds at the same
time (two `fid-dev` processes, load about 4).

## Findings

All six are the two open causes P1 and P2 (docs/verification/miscompile-log.md):

| Run | Input (shape) | Panic | Cause |
|-----|---------------|-------|-------|
| s3 [55] | `a{10000000000000000000000000003}` | overflow on multiplication, `rx_parse_brace` | P2 |
| s3 [7746] | `http://[::1(((…)]:89223372036854775808/` | overflow on multiplication, `String_parse_int` from `url_parse` | P1, the `[ipv6]:port` branch (not checked to be a number there) |
| s3 [13717] | a repetition count | overflow on addition, `rx_parse_brace` | P2 (the `+ digit` overflows instead of the `* 10`) |
| s4 [3070] | `x?y{2,39223372036854775808}` | overflow on multiplication | P2, the upper bound |
| s4 [9748] | `x?y{2,9223372036854775808…}` | overflow on addition | P2, the upper bound |
| s4 [14577] | `https://user:pw@example.com:808100000…/` | overflow on multiplication | P1 |

P3 (`xml_parse` on a stray `<`) is fixed in the working tree's xml.fd (the
XML 1.0 rewrite): `tests/verify/bugs/p3_xml_lt_oom.fd` prints ok on
`ccompile` (today's stdlib) and on `run` with HEAD's core.fd beside today's
xml.fd (the stage 0's interpreter does not know the builtin `p_region_word`
that today's core uses, so `run` with today's core stops in `Str_drop`
for every program: a stage-0 limit, not a parser finding),
`xml_parse("<")`, `"<a><b><<"` and `"<r><<x/></r>"` return at once through
the C-built driver, and the 4,444 xml inputs found nothing.

P1 and P2 are open: the fixes are in stdlib/url.fd and stdlib/regex.fd,
another group's files (described to it: a port of more than five digits or
above 65535 is -1, as url.fd documents for an unparseable port; the
repetition count saturates, so `RV_MAX_REPEAT` rejects it).
`tests/bootstrap/test_verify_vf15_parsers.fd` fails until both are fixed
(today it panics on its first line), and passes once they are.

## Repeating it

    FID=release/fid.exe bash scripts/fuzz/vf15_long_run.sh build/vf15-long

runs the same four runs (`TLS_N`, `ALL_N`, `SEEDS_TLS`, `SEEDS_ALL`), then
the P1-P3 repros and `test_verify_vf15_parsers.fd` through `run` and
`ccompile`, and writes `build/vf15-long/summary.txt`. One run by hand:

    python scripts/fuzz/fuzz_parsers.py --fid release/fid.exe -n 5000 --seed 1 --parsers tls
