# RL1, Nov 18: `gen_vs_c.py` on every backend, seeds 11-60

RL1 (docs/roadmap/llvm-roadmap.md): random programs built by every backend
and by the C path through clang/GCC must agree on output and exit status.
The first recorded run (seeds 1-10, Nov 16, all 11 backends) is in
[infra-runs-2026-11-16.md](infra-runs-2026-11-16.md#infra-runs-nov-16-batch-8-tl10-pl7-ad3-rl1-rl2); it found M12
and M13. This is the second run, with more seeds.

## Setup

- Compiler: the Nov 16 stage 0 (`stage0.exe`, one stage, built Nov 16
  12:33 from that day's tree). It does **not** hold this run's changes,
  among them the M12 and M13 fixes in `compiler/lower.fd`, so the default
  `--avoid all` steps around M12, M13, M14/M24, M1, M2, M3 and V1d.
- Stdlib: `git archive HEAD stdlib` in a directory given as `FID_HOME`, with
  `fid` run from outside the repository (fid takes `stdlib/` from its
  working directory first). With the working tree's stdlib the Nov 16
  compiler cannot run anything that pushes to a `Vec`: the working tree's
  `stdlib/core.fd` calls `p_region_word` (regions freed in one step, being
  written by another session), which that interpreter does not have
  (`Panic: Unknown function 'p_region_word'` in `rg_vec_fit`).
- Backends: run, ccompile, ccompile-O2, emit (pe_ir), nat (`emit --nat`),
  and ccompile for aarch64-linux, riscv64-linux and x86_64-linux (run under
  qemu-user / WSL). `emit:<linux target>` were left out: with this stage 0
  and HEAD's stdlib every Linux image imports the runtime primitive
  `nat_tls_set` from the C library and fails at load (`undefined symbol:
  nat_tls_set` on x86_64, the dynamic loader missing under qemu); seeds 11
  and 12 of a first try showed it on all three (the same mismatch is in
  vf5-vf7-2026-11-17.md and rl9-rl25-checks-2026-11-17.md). The final
  compiler and its own stdlib must run them.
- C oracle: `zig cc` -O0/-O2 and WSL's gcc -O0/-O2.

```
cd <scratch dir>        # not the repository: see above
FID_HOME=<dir with HEAD's stdlib/> python <repo>/scripts/fuzz/gen_vs_c.py -n 50 --seed 11 \
    --fid stage0.exe --backends run,ccompile,ccompile-O2,emit,nat,ccompile:aarch64-linux,ccompile:riscv64-linux,ccompile:x86_64-linux \
    --keep keep3 --log log3.txt
```

28 minutes (02:18-02:46, about 34 s per seed on a quiet machine).

## Result

    50 programs: 7 differ from C, 0 with a C oracle that disagrees with itself
    (by backend: run 0, ccompile 2, ccompile-O2 2, emit 5, nat 5,
     ccompile:aarch64-linux 2, ccompile:riscv64-linux 2, ccompile:x86_64-linux 2)

43 seeds agree on all 8 backends. Every disagreement is a known bug:

| Seed | Backends that differ | C says | Triage |
|------|----------------------|--------|--------|
| 26 | the 5 C-path backends | panic (exit 1) | **V1c**: `xs.push(xs[xs.len() \| xs.len()])` indexes one past the end; the C path reads 0 and prints a third line, run/emit/nat panic "Vec index out of bounds" |
| 43 | the 5 C-path backends | panic | **V1c**: `xs[if .. { xs.len() } else { xs.len() }]` (line 42), the same |

So the open causes RL1 sees with this compiler are **M7** (emit and
`--nat`: 5 of 50 programs) and **V1c** (the C path: 2 of 50). No new bug.
`run` agreed with C on all 50.

### Reductions

`scripts/fuzz/reduce.py keep3/<seed>.fd red<seed>.fd --bad emit --good
ccompile --match overflow` with the same compiler and stdlib:

- Seed 44, 5 lines in 32 tries: `var v8: u32 = (~((5 ^ 2) / 7) & 0xFFFFFFFF)`
  (0xFFFFFFFE), then `v8 as i8 * v8 as i8` in an i8 expression. C: −2 · −2
  = 4; emit: 254 · 254 overflows. **M7.**
- Seed 47, 10 lines in 83 tries: `v25: u16 = 65479` (0xFFC7), then
  `v25 as i8 + 15`. C: −57 + 15; emit: 199 + 15 overflows. **M7.**
- Seed 50, by hand (above): an i32 −4 `as i8` is 252 on emit. **M7.**
- Seed 49: the reducer was stopped at 28 lines (108 tries; its helper
  functions make each try slow). The panic is on `v5 = 15 + h0(..)` into an
  i8 whose operands come through `as i8` / `as i16` casts of wider values,
  emit and `--nat` only: counted as M7, **not confirmed by a reduction**.

The three reductions are now one repro,
`tests/verify/bugs/m7_emit_narrow_signed_arith.fd` (named in the M7 row of
the miscompile log). With this stage 0: `fid run` and `fid ccompile` print
the 8 expected lines; `fid emit` and `fid emit --nat` print `-2`, `4`, `199`
and stop with "Integer overflow on addition" (the u32 → i8 case of seed 44
comes out right there when the value is a constant; the u16 → i8 one does
not).

## What is left for RL1

- M7 is open. Its cause is in the native back ends: `Inst::IntTrunc` to
  `I8`/`I16`/`I32` zero-extends in compiler/pe_ir.fd (`movzx` /
  `mov eax, eax`) and in compiler/nat_ir.fd (`NEXT_ZB`/`ZH`/`ZW`), where a
  signed target needs the sign extension (`movsx` / `movsxd`, `NEXT_SB`/
  `SH`/`SW`). V1c is open (the C runtime's `p_vec_get` returns NULL past
  the end). Until both are fixed RL1 is not green.
- The run with the final compiler: every backend including
  `emit:<linux target>`, with `--avoid` minus `bitnot-narrow` and
  `for-continue` so seeds 1, 5 and 10 show the M12 and M13 fixes, and the
  seeds of this run.
- `gen_vs_c.py` wrote the outputs of the `emit:<target>` / `ccompile:<target>`
  backends to `<seed>.emit:<target>.out`, which on Windows is an NTFS
  stream of the file `<seed>.emit`, not a file (nothing showed them). Fixed
  Nov 18: the `:` becomes `-` in those names (`<seed>.emit-aarch64-linux.out`).
