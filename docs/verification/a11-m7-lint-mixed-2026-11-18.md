Four goals of the verify group, run on Nov 18 with the stage 0 of Nov 16
(`scratchpad/ws/stage0.exe`), not with this run's compiler, on a machine
other sessions were using (load 2-9). Each section says what the final

snapshot (the working tree's `compiler/`, `stdlib/` and tests, with HEAD's

## M7: `fid emit --checked-alloc` on the suite (release-roadmap M7)

`tests/checked_alloc/run.sh` with `SUITE=1` now compares each suite test's
checked build with the same program built without `--checked-alloc`
(`BASE=emit`, the default; `BASE=run` compares with `fid run` as before),
with a time limit on every build and run (`TIMEOUT`, 120 s), stdin from
/dev/null, a skip list (`tests/checked_alloc/suite-skip.txt`) and a result
file (`$OUT/suite.txt`). A test whose checked build stops with a
`(--checked-alloc)` report is a FAULT: a real use after free or overrun in
the program, core or the runtime, to be fixed, never skipped. The new block
layout (pe_ir_stubs.fd `PeirGen_gen_checked_malloc` records) is not in the
stage 0, so the suite run belongs to the final compiler.

A sample with the stage 0 (the folder's programs and the first 30 suite
tests, `LIMIT=30`): the five programs pass; 30 of 32 suite tests agree. The
two others:

- test_autodiff_grad: FAULT, "Use after free (--checked-alloc): the block
  of 512 bytes ... was freed; accessed at offset -16". Any `print` of an
  f64 natively does it: `stdlib/pe_runtime/base.fd` `pert_to_str_float`
  holds its 512-byte buffer in a `str` local (`var back: str =
  pe_buf_str(buf)`); `pe_trim_fraction_zeros` frees the buffer
  (`p_str_adopt`) and the local's drop at the function's end then reads the
  freed buffer's header (core `Str_drop` reads `s - 16`). A plain build
  reads freed memory and goes on. New program
  `tests/checked_alloc/float_print.fd` fails with the stage 0 and passes
  with the fix (no `str` local: `val same: bool =
  pe_c_strtod(pe_buf_str(buf), 0) == val; if same {`), checked on a
  scratch copy of the runtime. The fix is in another group's file.
- test_await_spawn_collections: the plain and the checked builds print
  different numbers; both are addresses, the stage 0 bug the test was
  written for (CA5, fixed after Nov 16), not the allocator's.

A second sample (`ONLY` = hash, vec, str, map, closure, enum, option, box,
rc, own, drop tests; 60 of them): 56 agree. Five FAULTs, all the same f64
print (test_vec_infer_elem, test_vec_infer_float_var,
test_vec_infer_from_var, test_vec_math, test_vecf64); two mismatches where
the plain stage 0 build itself prints addresses or crashes
(test_closure_capture_owner, test_vec_infer_tc); test_closure_capture_vec_borrow
does not build natively with the stage 0. No other use after free or
overrun was found in these 90 tests.
