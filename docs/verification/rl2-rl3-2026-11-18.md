# RL2 and RL3: tooling for the whole-suite runs, and what stage 0 shows (Nov 18)

RL2 asks for the suite on every backend and target; RL3 asks for the suite
with each mid-end pass and rule switched off to give the same output
(docs/roadmap/llvm-roadmap.md, track RL). Both are long whole-suite runs.
They need the compiler built from this tree, which is built once at the
end of the batch, so this page records the tooling, the checks of it, and
what the Nov 16 stage-0 compiler showed on small samples. The recorded
whole-suite runs go in pages of their own (see "Recording a run" below).

## RL2: the suite on every lane

Already in the tree: `scripts/suite-all.sh` (ten lanes: C and native
x86_64/aarch64/riscv64-linux, C wasm32-wasi, C x86_64-windows, pe_ir and
`--nat` on Windows), `.github/workflows/suite-all.yml` and `tier1.yml`
(every lane on push and pull request, checked by
`scripts/suite-lanes-check.sh`), and the WASI `SO_ERROR` fallback in
compiler/codegen_c.fd.

New:

- `scripts/verify/suite-all-report.py` reads a run's folder (default
  build/suite-all) and writes, per lane, passed / failed / did not build /
  skipped, each failure's cause, and the failing tests grouped by the lanes
  they fail on, with where to look first. It also lists the Linux binaries
  that import one of the runtime's own names from a shared library, and
  the tests whose lanes disagree. Causes it names: a runtime name bound
  by ld.so ("symbol lookup error: undefined symbol: X"), a missing loader
  or C library, a timeout, a crash (signal, Windows exception), a panic,
  exit code or output that differs (the first differing line), a compiler
  panic or build error (paths and numbers dropped for grouping), a zig
  cache race, running out of memory. `--selftest` checks each of these on
  made-up lanes.
- `scripts/suite-all.sh` runs the report at the end of every run:
  `$OUT/report.md` and `$OUT/report.txt`, for the run's own lanes only
  (`--lanes`, since OUT can hold lanes of an earlier run).
- `tests/tooling/rl2-suite-report-check.sh`. Checks 1-4 need no
  compiler: the report's selftest, the ten lanes, the workflows (and their
  selftest), and the WASI fallback. With `FID=`: hello.fd for wasm32-wasi
  under node (check 5). Check 6 builds hello.fd and
  test_verify_rl3_rule_identities.fd for the three Linux targets and
  checks that no binary imports a runtime name.

### Found with stage 0: Linux executables import runtime builtins

The riscv64 lane failure that the roadmap names ("binaries importing
runtime builtins (nat_tls_set and others) from libc.so.6") is not specific
to RISC-V. With the stage-0 compiler of Nov 16, `fid emit
tests/bootstrap/hello.fd --target riscv64-linux` and `--target
aarch64-linux` (x86_64-linux the same) give a dynamic executable. It names
`/lib/ld-linux-riscv64-lp64d.so.1` and imports 20 names that every
executable defines itself:

    nat_tls_set nat_frame_fp nat_os nat_sig_handler nat_sig_restorer
    nat_fn_names nat_arch nat_tls_get nat_start_sp nat_frame_ret
    nat_frame_next nat_atomic_cas nat_atomic_store nat_atomic_add
    nat_fn_table nat_clone_thread nat_atomic_load
    p_sensitive_check p_sensitive_free p_sensitive_remark

With `FID_NAT_OFF=ldyn` the same hello.fd is static,
`scripts/bin-target-check.py riscv64-linux` passes it, and under
qemu-riscv64 in WSL it prints what `fid run` prints. The cause is the CI2
branch of compiler/nat_ir.fd `ng_gen_call_std`: an `extern` declaration
the program does not define as a function is bound by the dynamic linker.

- The `nat_*` names are fixed in the tree (F8, `ng_is_own_prim`; see
  docs/reference/f8-native-linux-triage.md).
- The `p_sensitive_*` names are not. stdlib/core.fd declares them with
  `extern fn p_sensitive_check(...)`, and its Vec code calls them, so
  nearly every program reaches them. The image does define them, as
  stdlib/linux_runtime/base.fd's `pert_sensitive_check` and the rest:
  `ng_resolve` maps `p_X` to `pert_X`. The CI2 test checks only
  `ng_has_fn(g, call_name)` and `ng_is_own_prim`, never the resolved
  name. So with today's tree, every native Linux executable that uses a
  Vec still imports `p_sensitive_check`, `p_sensitive_free` and
  `p_sensitive_remark` from libc.so.6, and stops at load. The fix is one
  more condition on that branch: a name `ng_resolve` sends to a function
  the image has is not a C function. It is a hunk for nat_ir.fd's owners
  (the "needs another group" list of this batch).
  `tests/tooling/rl2-suite-report-check.sh` check 6 and
  tests/nattools/f8_static_prims_check.sh both fail until it is in. With
  stage 0, check 6 fails on all six binaries.

Other stage-0 results: hello.fd through C for wasm32-wasi builds and runs
under node (check 5 passes). The report run over the Nov 16 smoke run's
folder (build/suite-all, 4 tests) names the two failing lanes of that
run. c:wasm32-wasi: "use of undeclared identifier 'SO_ERROR'", fixed in
codegen_c.fd since. native:x86_64-windows-pe: "C compilation failed
(tried gcc, clang, cc)", a run without CC.

## RL3: one rule off at a time

Already in the tree: `scripts/pass-matrix.sh` rounds 1-4 (iropt passes,
backend passes and rule groups, the opt-in mid-end, e-graph families with
`FID_EGRAPH_OFF`, which compiler/egraph.fd reads) and round 5, which runs
only when compiler/rules.fd reads `FID_RULES_OFF`.

New:

- docs/verification/kill-switches.md, section "Single rules":
  `FID_EGRAPH_OFF` with its 14 families, and `FID_RULES_OFF` with the 27
  rule indexes. Before, the page said nothing reads either variable.
- `tests/bootstrap/test_verify_rl3_rule_identities.fd`: one use of each
  rule of `ru_rules` on a value the mid-end cannot know. With stage 0 and
  `fid emit --nat`, `FID_RULE_STATS=1` shows every one of the 27 rules
  firing, and the program prints its Expected output through `fid run`
  and `--nat`.
- `tests/tooling/rl3-rules-off-check.sh`:
  - Source checks: rules.fd reads `FID_RULES_OFF` and folds it into its
    memo key; nat_ir's cache key holds both variables; the doc names
    every family; pass-matrix's selftest passes; round 5 tries as many
    rules as `ru_rules` has.
  - With `FID`: `fid test-rules`; every rule firing; each rule off on its
    own (0 hits for that rule, the others still firing, the same output);
    all off.
  - The memo (CS1): `FID_RULES_OFF=all` after an all-on build that shares
    the memo file must give the executable of `FID_NAT_OFF=rules`, not the
    all-on one.
  - Each e-graph family off: the same output.

  With stage 0 (`RULES=0`), the family checks pass and the `FID_RULES_OFF`
  checks fail (stage 0 does not read it). The memo check is skipped:
  stage 0 has no memo.
- `scripts/pass-matrix.sh RESUME=1`: a run that finished before (its
  summary in `$OUT/<tag>.line`, its results.txt there) is not run again.
  The whole matrix is about 95 suite runs per target, so it can be done in
  several sittings. Its selftest checks both ways.
- `scripts/verify/pass-matrix-report.py`: per target, the switches tried,
  those that differ with their tests (PASS -> FAIL, output), tests that
  differ under many switches (suspect: rerun before blaming a switch), and
  switches that differ on every target. `--selftest`.
- `scripts/verify/rl3-matrix-all.sh`: the matrix on every native target
  the host runs (resuming by default), then the report in
  build/pm/report.md.

The change rules.fd still needs (for its owners): `ru_rules_off`, which
reads `FID_RULES_OFF` (indexes, or `all`) and sets a listed rule's `op` to
0 so it never matches, keeping its place and name. `rules_run` calls it
after `ru_rules()`, so `fid test-rules`, the SMT obligations and
`FID_NAT_MUTATE` still see every rule. The memo key `cfg_h` gets
`hash_source(env_or_empty("FID_RULES_OFF"))`.

## Recording a run

With the compiler of the final build (`$FID`):

    AGREE=1 FID=$FID JOBS=4 bash scripts/suite-all.sh
    cp build/suite-all/report.md docs/verification/rl2-suite-all-<date>.md

    FID=$FID JOBS=4 bash scripts/verify/rl3-matrix-all.sh   # rerun to resume
    cp build/pm/report.md docs/verification/rl3-pass-matrix-<date>.md

Each copied report then gets its triage: a finding goes to
miscompile-log.md with a test, a flaky test to scripts/flake-repeat.sh.
