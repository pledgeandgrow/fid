# RL15 and RL22: the sanitized compiler and the two-path release run (Nov 18)

Two goals of the own-backend roadmap's reliability track
(docs/roadmap/llvm-roadmap.md, track RL):

- RL15: the compiler itself under AddressSanitizer and
  UndefinedBehaviorSanitizer through the C path, finding its own memory
  errors.
- RL22: two independent paths kept on purpose, our backend and the C path;
  a release ships only when both agree on the suite.

Both are runs of the compiler built from this tree. This batch builds the
tree once, at its end, so this page records the tooling written for the
runs, the checks of that tooling that ran here, a stage-0 sample of the RL22
run, and the exact commands for the validation runs.

## RL15: the compiler under ASan and UBSan

### What was there

`COMPILER=1 scripts/sanitize.sh` (Nov 15) builds fid's C with the
sanitizers through `scripts/verify/build-variant.sh` (`EXTRA_CFLAGS`), then
has that compiler check, lower to C and interpret each test, and with
`SELF=1` compile itself. It needs a Linux or macOS `fid`, because
build-variant.sh runs `$FID dump-c compiler/main.fd` and compiles the
result on the same host. This machine has only Windows compilers. Its WSL
(Kali, gcc 15.2.0 with libasan and libubsan, no clang) has no `fid`.
`scripts/sanitize-wsl.sh` sanitizes test programs from Windows, not the
compiler.

### New: scripts/verify/sanitize-compiler-wsl.sh

It runs the RL15 check from Windows, with WSL doing the Linux part:

1. **Windows.** It takes a snapshot of `compiler/` and `stdlib/` (other
   sessions edit the tree during a run, AGENTS.md 26). The Windows `$FID`
   writes the compiler's C from the snapshot with `OS=Linux`, so `@cfg(os)`
   and the platform modules take the Linux side (compiler.fd reads `OS`
   for the host). The script then wraps `main` on a big-stack thread
   (`STACK_MB`, default 1024: ASan's red zones make frames larger) and
   splits the C into `SPLIT` units with `fid split-c`. `FIDC=<file>` uses a
   C file that already exists, for example `release/fid-dev.c` from the
   final build.
2. **WSL build.** `fid-plain` is built at -O2 with no sanitizers. With
   `LINUX_C=1` (the default), fid-plain then writes the compiler's C again,
   on Linux, and the script records whether that C is the same as the C
   written on Windows. `fid-san` is built from the Linux C at `SAN_OPT`
   (default -O1) with `-fsanitize=$SAN` (default address,undefined) and
   `-fno-sanitize-recover=undefined`. `UB_RECOVER=1` lists every UB site of
   a run instead of stopping at the first. Units compile `JOBS` at a time
   (default 3).
3. **WSL tests.** Each test goes through both compilers for each of
   `STEPS` (default `check dump-c run`), from the snapshot, with `tests/`
   and `examples/` linked in. A step is a finding when:
   - fid-san's stderr has a sanitizer report, or
   - fid-san's stdout or exit status differs from fid-plain's, and
     fid-plain gives the same result twice.

   A step whose two plain runs differ from each other (times, random
   values) is judged on sanitizer reports alone. A timeout that happens
   only under the sanitizers is listed as slow, not as a failure.
   Expected-fail tests are included: their errors are compiler paths too.
4. **`SELF=1`.** fid-san compiles `compiler/main.fd`, and its C must equal
   fid-plain's.

The script writes `$OUT/summary.san` and `$OUT/report.md` (a table of
findings with the first report line of each), and exits 1 on a finding.
`SELFTEST=1` replaces the compiler with a small stand-in, so no `fid` is
needed. The stand-in is built the same two ways in WSL:
- `clean.fd` must pass every step;
- a heap overrun in `run` must be reported as a sanitizer finding;
- a division by zero in `run` must be reported as a sanitizer finding;
- the `SELF=1` step must pass.

Notes for reading a run:
- **Signed overflow.** Fid's C is compiled with `-fwrapv`, as every build
  of it is, so signed overflow is defined and UBSan reports none.
  Overflow checks are the language's own, in the generated code.
- **Leaks.** `detect_leaks=0`: the compiler frees little before it exits,
  by design. Leaks are `fid run --leaks` and scripts/leak-check.sh.
- **Allocator.** Under ASan the C runtime takes every block from `calloc`
  (`P_SAN_ALLOC` in compiler/codegen_c.fd), so a use after free inside the
  compiler's own block pools is reported, not hidden.
- **Linux clang.** The goal names Linux clang. With `sudo apt install clang`
  in WSL the script uses clang on its own (or `WSL_CC=clang`). Until then
  it uses gcc, whose ASan and UBSan cover the same errors.

### Run here

- `SELFTEST=1 SELF=1 bash scripts/verify/sanitize-compiler-wsl.sh`: WSL
  gcc 15.2. Result: `sanitize-compiler-wsl selftest: OK`. 8 steps were
  clean. The overrun and the division by zero in `run` were each reported
  ("runtime error: store to address ... with insufficient space", "runtime
  error: division by zero"). The SELF step passed.
- `tests/tooling/rl15-sanitize-compiler-check.sh`: checks 1 (scripts parse;
  sanitize.sh keeps COMPILER=1 and SELF=1) and 2 (the selftest) passed.
  Check 3 needs `FID`.

### Not run

The run itself was not done. It builds the compiler twice in WSL, and this
batch may not build the compiler. So there are no reports yet to fix or
file. Running it is the validation step below. Each report it finds is
then fixed in compiler/*.fd or the C runtime (compiler/codegen_c.fd
`emit_runtime_impl`), or filed in docs/verification/miscompile-log.md with
the test and its first report line.

### Validation with the final compiler

```bash
# tooling, then a quick real check (two tests, check + dump-c)
bash tests/tooling/rl15-sanitize-compiler-check.sh                 # 1, 2 OK
FID=$FID bash tests/tooling/rl15-sanitize-compiler-check.sh        # 3 OK too
# the run (hours: about 4 compiler runs per step per test under ASan)
FID=$FID OUT=/c/tmp/rl15 SELF=1 bash scripts/verify/sanitize-compiler-wsl.sh
#   or a first pass:  FID=$FID OUT=/c/tmp/rl15s SAMPLE=150 SELF=1 bash ...
#   with the final build's C:  FIDC=release/fid-dev.c FID=$FID ...
```

The run passes when the last line of `$OUT/summary.san` says `0 failed`
and the `SELF` step passed. Copy the summary and `$OUT/report.md` into a
page of this folder. Every FAIL line must be fixed or filed as above.

## RL22: the C path and our backend agree on the suite

### What was there

- `AGREE=1 scripts/suite-all.sh` fails when a test passes on one lane and
  fails or does not build on another.
- docs/reference/releasing.md step 2 runs it.
- The WASI `SO_ERROR` gap is fixed (compiler/codegen_c.fd, its `__wasi__`
  block; tests/tooling/rl2-suite-report-check.sh check 4).
- `scripts/verify/suite-all-report.py` writes each run's report.

AGREE compares every lane with every other, across targets too. Nothing
compared the two paths target by target, said which side failed, or kept a
record of a disagreement that has to wait for its fix.

### New

- **`scripts/verify/rl22-paths.py`** reads a suite-all run's folder (no
  compiler) and pairs each C-path lane with the own-backend lanes of its
  target:

  | C path | own backend |
  |---|---|
  | `c:x86_64-linux` | `native:x86_64-linux` |
  | `c:aarch64-linux` | `native:aarch64-linux` |
  | `c:riscv64-linux` | `native:riscv64-linux` |
  | `c:x86_64-windows` | `native:x86_64-windows-pe` (pe_ir) |
  | `c:x86_64-windows` | `native:x86_64-windows` (`--nat`) |
  | `c:<arch>-macos` | `native:<arch>-macos` |

  For each pair it lists:
  - the tests that pass on one path and fail or do not build on the other,
    each with its cause (suite-all-report.py's readers of the lane files),
  - the tests that fail on both (suite failures, RL2),
  - the lanes with no partner (`c:wasm32-wasi`).

  Every disagreement must be either fixed or recorded in
  `scripts/verify/rl22-recorded.txt` (`<pair> <test> <reason>`, wildcards
  allowed in the pair). The script exits 1 while one is neither. It lists
  stale records (the test agrees now), and `--strict` fails on them.
  `--selftest` checks it on made-up lane folders.
- **`scripts/verify/rl22-recorded.txt`**: empty. No disagreement is
  recorded yet.
- **`scripts/verify/rl22-release-run.sh`**: the release run. It runs
  `AGREE=1 scripts/suite-all.sh` with `$FID` on every lane the host runs
  (or the lanes given), then rl22-paths.py, then writes one page,
  `$OUT/rl22-release-<date>.md`, to copy here. The page holds the compiler,
  host, lanes and time, both exit statuses, the pair comparison and the
  per-lane report. The script's exit status is suite-all's, which is the
  release gate. `PAIRS=1` gives the pair check's status instead.
- **`tests/tooling/rl22-paths-check.sh`** has four checks:
  1. the selftest;
  2. rl22-recorded.txt is well formed and each pattern matches a real pair;
  3. the scripts parse, and releasing.md still runs AGREE=1;
  4. with `FID`, a smoke release run of hello and test_hashmap on the
     host's C lane and native lane.

### Run here

- `python3 scripts/verify/rl22-paths.py --selftest`: ok.
  `tests/tooling/rl22-paths-check.sh`: checks 1-3 OK, check 4 skipped (no
  `FID`).
- rl22-paths.py over the Nov 16 smoke run (build/suite-all, 4 tests, 10
  lanes):
  - 4 of 5 pairs agree on all 4 tests.
  - `c:x86_64-windows` against `native:x86_64-windows-pe`: 4 tests "did
    not build" on pe_ir, with "C compilation failed". This was the
    `OS=windows` export of cross-test.sh, fixed that day (infra-runs-2026-11-16.md).
    The tool names it: an open disagreement of that run.

### A stage-0 sample of the release run

This is the release run's tooling end to end, on a sample. It is not the
release run.

Setup:
- Command: `FID=stage0 JOBS=1 CC="zig cc" TESTS="<23 tests>"
  scripts/verify/rl22-release-run.sh` on five lanes: `c:x86_64-windows`,
  `native:x86_64-windows-pe`, `native:x86_64-windows`, `c:x86_64-linux`,
  `native:x86_64-linux` (in WSL).
- Compiler: the Nov 16 stage 0 (`fid 0.8.0-unstable`).
- Tree: HEAD's compiler/, stdlib/ and tests/bootstrap/ (`git archive
  HEAD`) with the working tree's scripts/, because stage 0's interpreter
  cannot run the working tree's core.fd.
- Tests: hello.fd and every 20th non-expected-fail test of HEAD's
  tests/bootstrap.
- Time: about 75 minutes, one fid at a time.

Result: suite-all exited 6 (5 failing lanes, 19 tests disagreeing across
lanes). rl22-paths.py found, pair by pair:

| C path | own backend | compared | own backend only fails | C path only fails | both fail |
|---|---|---|---|---|---|
| `c:x86_64-linux` | `native:x86_64-linux` | 21 | 18 | 0 | 3 |
| `c:x86_64-windows` | `native:x86_64-windows` (`--nat`) | 21 | 1 | 1 | 2 |
| `c:x86_64-windows` | `native:x86_64-windows-pe` | 21 | 2 | 1 | 2 |

Each disagreement, and what it is:

- **`native:x86_64-linux`, 17 tests**: "symbol lookup error: undefined
  symbol: nat_tls_set" (exit 127). Stage 0 binds the machine layer's own
  primitives from libc.so.6. This is fixed in the tree (F8: nat_ir.fd
  `ng_is_own_prim`; rl2-rl3-2026-11-18.md). It is not recorded, because the
  final compiler must show it gone. The `p_sensitive_*` imports that page
  names are still open in nat_ir.fd and will show here if they remain.
- **`test_lib_ota`, both own-backend lanes and native Linux**: the build
  fails with "@secret/@sensitive errors" in `crypto_hmac_sha256`. On a
  native build the runtime is merged into the program, and the secrecy
  check reached pe_runtime's `pe_wq_push` through any `_push` name. This
  is fixed in the tree (known-bugs 2g.71, compiler/secrecy.fd
  `sec_index_method`). Not recorded.
- **`test_process` on pe_ir**: `process_stdout` returned stderr's text
  ("p2 e_out"). This is fixed in the tree's stdlib/pe_runtime/base.fd
  `pert_process_run` (known-bugs 2g.43: the strings are handed to the
  record as owners). Not recorded.
- **`test_lib_ui` through C on Windows**: zig cc cannot find the SDL2 and
  SDL2_image libraries. stdlib/sdl.fd declares `extern "C" link "SDL2"`, so
  the C path links them even though the test calls nothing in them; pe_ir
  and `--nat` import per call. This is the host's environment, not a
  compiler bug, and is **recorded** in scripts/verify/rl22-recorded.txt
  (the only line there).

Failures on both paths, so no disagreement:
- `test_c_callback`: the interpreter cannot call C, so there is no correct
  reference (sanitizers-2026-11-17.md).
- `test_pe_dll_import`: its C declares `BCryptGenRandom` with types that
  conflict with windows.h; pe_ir runs it, but the exit code differs from
  the interpreter's.

Skipped: two tests without a reference (`test_x25519` timed out in the
interpreter; `test_result_context`).

With the record, 21 disagreements are open, and all 21 are fixed in the
tree. The final compiler's run must show them gone, or each must be fixed
or recorded with its cause.

### Not run

The release run: `AGREE=1` on the whole suite (the ~1,100 tests of
tests/bootstrap), every lane, with the release compiler. That compiler is
built once, at the end of this batch. At this machine's speed (one fid at
a time) that is about 10 lanes × 1,100 tests × 10-20 s, a day or more;
JOBS=4-8 shortens it.

### Validation with the final compiler

```bash
python3 scripts/verify/rl22-paths.py --selftest                 # ok
bash tests/tooling/rl22-paths-check.sh                          # 1-3 OK
FID=$FID CC="zig cc" bash tests/tooling/rl22-paths-check.sh     # 4 OK too
# the release run (whole suite, every lane the host runs)
FID=$FID JOBS=4 CC="zig cc" OUT=build/rl22 bash scripts/verify/rl22-release-run.sh
cp build/rl22/rl22-release-$(date -u +%Y-%m-%d).md docs/verification/
```

RL22 is met when `rl22-release-run.sh` exits 0 (AGREE=1: every lane
passes, no two disagree), or when every remaining C-path/own-backend
disagreement is fixed or recorded with its cause (`PAIRS=1` exits 0). The
recorded page is then copied into this folder. The stage-0 disagreements
above (nat_tls_set, test_lib_ota, test_process) must not appear.
